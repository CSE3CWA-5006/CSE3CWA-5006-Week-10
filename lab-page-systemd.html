Lab: Deploy the Web Application to AWS EC2

In this lab, you will deploy the supplied Week 10 Express web application to an Ubuntu virtual machine on Amazon EC2. You will start an AWS Academy lab session, launch an Ubuntu EC2 instance, configure the security group, connect to Ubuntu, clone the project from GitHub, run the supplied deployment scripts, and test the public website in a browser.

Week 10 code: https://github.com/CSE3CWA-5006/CSE3CWA-5006-Week-10

 

What you will deploy

The Express application listens privately on 127.0.0.1:3000. Ubuntu systemd keeps the application running as a service named week10-nodeapp. Nginx accepts public HTTP traffic on port 80 and forwards it to the private application. You do not need to open port 3000 in the EC2 security group.

1. Start AWS Academy and open AWS

  1. Sign in to the AWS Academy course provided by the teaching team.
  2. Open the required Learner Lab or lab environment.
  3. Choose Start Lab or the equivalent start button.
  4. Wait until the lab status shows that the AWS environment is ready.
  5. Open the AWS Management Console.
  6. Check the Region shown in the top-right area of the AWS console and stay in that Region for the whole lab.

AWS Academy environments can restrict services, instance types and connection methods. If the Academy lab gives you a browser-based connection option, you may use that instead of local SSH.

2. Launch an Ubuntu EC2 instance

  1. In the AWS Management Console, search for EC2.
  2. Open the EC2 service.
  3. Choose Instances, then choose Launch instance.
  4. Use the following settings.
Setting Use for this lab
Name week10-webapp
AMI A current Ubuntu Server LTS image available in the Academy environment
Instance type A small instance type permitted by AWS Academy, such as t2.micro or t3.micro if available
Key pair / connection method Select an existing key pair, create a new key pair if permitted, or use the Academy browser-based connection method

Important: choose Ubuntu Server LTS, not Amazon Linux. This lab uses Ubuntu commands such as sudo apt update and sudo apt install.

Configure the security group with these inbound rules:

Traffic Port Source
SSH 22 Your current IP address where local SSH is permitted; otherwise use the Academy connection instructions
HTTP 80 0.0.0.0/0 for this public teaching website

Do not add an inbound rule for port 3000. Port 3000 is only used privately on the EC2 instance.

Launch the instance. Wait until the instance state is Running and the status checks have passed. Copy and keep the Public IPv4 address; you will use it later in the browser.

3. Connect to Ubuntu

Select the instance and choose Connect. Use the connection option available in your AWS Academy environment.

If you use the browser-based EC2 connection, follow the prompts shown by AWS. If you use SSH from your own computer, copy the exact command shown by the EC2 console. Ubuntu EC2 images normally use the username ubuntu.

ssh -i YOUR_KEY_FILE.pem ubuntu@YOUR_PUBLIC_IPV4_ADDRESS

Replace YOUR_KEY_FILE.pem and YOUR_PUBLIC_IPV4_ADDRESS with your own values. The public GitHub repository used in this lab does not require a GitHub username or password to clone.

After connecting, confirm that you are on the remote EC2 instance:

whoami
hostname

On a standard Ubuntu EC2 instance, whoami should normally return ubuntu.

4. Download the Week 10 project from GitHub

Clone the repository directly to the Ubuntu user's home directory. The service script uses the week10-nodeapp directory where you run it, so make sure you run the commands from inside that directory.

sudo apt update
sudo apt install -y git

cd ~
git clone https://github.com/CSE3CWA-5006/CSE3CWA-5006-Week-10.git
cd CSE3CWA-5006-Week-10/week10-nodeapp
chmod +x deploy/*.sh
ls

You should see files including package.json, package-lock.json, server.js, .env.example and the deploy directory.

5. Prepare Ubuntu and install dependencies

Run the supplied setup script:

./deploy/setup_ubuntu_ec2.sh

This script installs ca-certificates, curl, git, nginx, Node.js 24.x from NodeSource, npm dependencies, creates .env from .env.example when required, starts Nginx, and checks JavaScript syntax.

Confirm the installed versions:

node -v
npm -v
nginx -v

node -v should show a version beginning with v24..

6. Test the Node.js application privately

Start the application directly before installing it as a service:

npm start

The application should report that it is listening on http://127.0.0.1:3000.

Keep that terminal running. Open a second SSH/browser terminal to the same EC2 instance and run:

curl http://127.0.0.1:3000/
curl http://127.0.0.1:3000/api/health
curl http://127.0.0.1:3000/api/time

The first command should return HTML. The two API commands should return JSON. Return to the terminal running npm start and press Ctrl + C.

7. Run the application as a systemd service

Install and start the supplied service:

./deploy/install_app_service.sh

The script creates /etc/systemd/system/week10-nodeapp.service, points it at the current week10-nodeapp directory, enables it, restarts it, and prints its status.

Verify the service and private endpoint:

sudo systemctl status week10-nodeapp --no-pager
curl http://127.0.0.1:3000/api/health

The service status should show active (running), and the curl command should return JSON.

8. Configure Nginx

Install the supplied Nginx reverse proxy configuration:

./deploy/install_nginx_proxy.sh

The script copies deploy/week10-nodeapp.nginx into Nginx, enables the site, removes the default site, validates the Nginx configuration with sudo nginx -t, and reloads Nginx.

Test the complete local web path through Nginx:

curl http://127.0.0.1/
curl http://127.0.0.1/api/health
curl http://127.0.0.1/api/time

9. Open the public website

Return to the EC2 console and copy the instance's current Public IPv4 address. On your own computer, open:

http://YOUR_PUBLIC_IPV4_ADDRESS
http://YOUR_PUBLIC_IPV4_ADDRESS/api/health
http://YOUR_PUBLIC_IPV4_ADDRESS/api/time

Replace YOUR_PUBLIC_IPV4_ADDRESS with the actual address of your EC2 instance.

 

Deployment complete

If the main page loads and /api/health returns JSON, the Week 10 application is running on AWS EC2 and is publicly accessible through Nginx on port 80.

10. Troubleshooting

Check one layer at a time. Do not change several settings at once.

Problem Check
SSH connection fails Confirm the instance is running, use its current public IPv4 address, and check the SSH security-group rule or Academy connection method.
git clone fails Confirm the repository URL and check that the EC2 instance has outbound Internet access. This public repository should not ask for a GitHub password.
Node.js version is not 24.x Run ./deploy/setup_ubuntu_ec2.sh again and check the NodeSource installation output.
The app does not start with npm start Run npm install, then npm run check, and read the error output.
The service is not running Run sudo systemctl status week10-nodeapp --no-pager.
You need application logs Run sudo journalctl -u week10-nodeapp -n 50 --no-pager.
Browser shows 502 Bad Gateway Check the application service and confirm that curl http://127.0.0.1:3000/api/health succeeds.
Nginx configuration fails Run sudo nginx -t and read the reported error.
Local curl works but the browser times out Check the public IPv4 address and confirm that the EC2 security group allows inbound TCP port 80.

11. Evidence and cleanup

Before ending the lab, capture evidence showing:

  • the EC2 instance running in the AWS console;
  • sudo systemctl status week10-nodeapp --no-pager showing active (running);
  • sudo nginx -t reporting a successful configuration test;
  • the Week 10 application open in your browser; and
  • /api/health returning a successful JSON response.

Remove the Week 10 application service and Nginx site configuration:

./deploy/cleanup_lab.sh

Finally, stop or terminate the EC2 instance according to the AWS Academy instructions. Do not leave teaching resources running unnecessarily.

This lab intentionally uses HTTP for a controlled teaching deployment. A production Internet-facing application would normally require additional controls such as HTTPS, domain configuration, stronger access restrictions, production secrets management, monitoring, backup and an architecture appropriate to the workload.
